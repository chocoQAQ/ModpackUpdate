# 配置文件说明

本文对应 ModpackUpdate 0.3.0-preview.6，适用于 Fabric、NeoForge、Forge 和 Quilt，具体游戏与加载器版本见 [构建目标](building.md)。各构建使用相同配置字段，加载器类型由模组自动识别。整合包作者通过 `config.json` 设置更新地址和安装策略，客户端通过 `installed.json` 记录已安装版本及文件基线。

## 文件位置与生效时机

从 0.3.0-preview.6 开始，更新入口请求自动携带 `X-ModpackUpdate-Protocol-Version: 2`，无需新增配置项。服务可在同一个 `update-service-url` 根据该字段返回 v1 或 v2；无字段请求应返回 v1，让旧客户端先完成更新器升级。纯静态 v1 服务仍兼容。具体请求和缓存规则见 [发布协议](publishing-protocol.md#请求协议版本与同-url-迁移)。

更新入口返回 `{"changed":"https://新服务/清单.json"}` 时，客户端会校验并原子保存新的 `update-service-url`，本次继续游戏，下次启动才访问新地址。其余设置和安装记录保留，`full-pack-url` 不会随之修改；无效通知或保存失败会记录错误并保留原配置。详情见 [服务地址迁移](publishing-protocol.md#服务地址迁移changed)。

配置、安装记录及文件基线索引统一位于实例的 `ModpackUpdate/config/` 下。使用版本隔离的启动器时，应以该实例实际使用的游戏目录为准。

```text
<游戏根目录>/ModpackUpdate/config/config.json
<游戏根目录>/ModpackUpdate/config/installed.json
<游戏根目录>/ModpackUpdate/config/file-indexes/<SHA-512>.json
```

首次正常启动检查时，如果 `config.json` 缺失，程序会生成下方默认配置。配置在每次启动检查时读取，修改后于下次启动生效。文件使用 UTF-8 编码、JSON 对象和本文列出的字段名称，布尔值使用 `true`、`false`。

省略字段时采用程序默认值。未知字段会被忽略，字段拼写需要与文档一致。填写时使用标准 JSON，所有键和字符串使用双引号，并去掉注释和末尾多余的逗号。

## 默认配置

```json
{
  "enable": false,
  "update-service-url": "",
  "full-pack-url": "",
  "pack-id": "",
  "silent-update": false,
  "delete-replaced-mods": false,
  "timeout-seconds": 10,
  "check-timeout-seconds": 60,
  "cache-max-mib": 2048,
  "backup-retention-count": 0,
  "protected-paths": [
    "options.txt",
    "optionsof.txt",
    "servers.dat",
    "saves/",
    "screenshots/"
  ]
}
```

| 字段 | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `enable` | 布尔值 | `false` | 启用启动时的版本检查 |
| `update-service-url` | 字符串 | `""` | 发布元数据 JSON 的 URL |
| `full-pack-url` | 字符串 | `""` | 接口清单下载失败时使用的完整 `.mrpack` URL，留空关闭兜底 |
| `pack-id` | 字符串 | `""` | 当前整合包的固定标识，启用更新时需填写 |
| `silent-update` | 布尔值 | `false` | 自动接受新版本，按下文规则显示冲突选择和安装结果 |
| `delete-replaced-mods` | 布尔值 | `false` | 成功安装后清除本次被覆盖的旧模组备份 |
| `timeout-seconds` | 整数 | `10` | 网络连接与请求的超时秒数 |
| `check-timeout-seconds` | 整数 | `60` | 启动时获取发布信息、下载和解析兜底包的总时限，范围 2–600 秒 |
| `cache-max-mib` | 整数 | `2048` | 空闲时保留的下载缓存上限，单位 MiB；`0` 表示安装结束后不保留下载缓存 |
| `backup-retention-count` | 整数 | `0` | 自动保留最近几次已完成事务的备份；`0` 或负数不自动删除备份 |
| `protected-paths` | 字符串数组 | 上方五个路径 | 在安装计划中跳过的文件与目录 |

## 启用更新

作者可以使用下面的最小配置，其余字段采用默认值。示例域名需要替换成自己的更新地址。

```json
{
  "enable": true,
  "update-service-url": "https://updates.example.com/my-pack/latest.json",
  "pack-id": "my-pack"
}
```

`update-service-url` 指向发布元数据，其中包含版本、公告、索引 URL、overrides 信息和完整包 URL。地址格式与内容约定见发布协议。生产地址使用 HTTPS，本地调试支持 `http://localhost` 和 `http://127.0.0.1`，可以附带端口。URL 中的用户名、密码和 `#` 片段会被拒绝。 [发布协议](publishing-protocol.md)

`pack-id` 在配置、发布元数据和已有安装记录中应保持一致。客户端对该标识进行区分大小写的匹配，版本升级期间保持同一标识。

正常接口通过发布元数据的 `release-id` 和本地安装记录判断新版。远程编号大于本地编号时才进入更新流程；已通过兜底安装的同版本会跳过。展示用版本号保存在 `installed.json`，兜底源按下文规则判断。启用配置后，作者还应为当前发行版本生成初始安装记录，随整合包分发。 [打包流程](packaging.md)

`enable: false` 会跳过新的更新检查。如果上次安装中断并留下 `ModpackUpdate/transaction.json`，程序仍优先恢复该事务，以便下次启动获得一致的文件状态。

存在未完成事务时，即使独立更新程序启动失败或异常退出，也会阻止游戏继续启动；无法确认事务记录是否存在时同样阻止。排查时查看 `ModpackUpdate/runtime/` 日志及实例目录权限。没有未完成事务的普通离线或检查错误仍允许继续游戏。

## 完整整合包兜底

在配置中增加可选字段：

```json
"full-pack-url": "https://downloads.example.com/my-pack/latest.mrpack"
```

仅在 `update-service-url` 的发布元数据无法下载时（例如 HTTP 404 / 5xx、网络连接失败或超时）尝试此地址。正常取得发布清单时，即使没有更新，也不会请求兜底 URL。已下载清单的 JSON 格式错误、包 ID 不匹配或其他内容校验失败不会触发兜底，索引或 overrides 下载失败也不会触发这个配置入口；后者继续使用发布清单内原有的 `full-pack` 兜底。

兜底地址必须指向当前实例对应的完整 Modrinth `.mrpack`，不是网页或 overrides ZIP。遵循同样的 HTTPS / 本地 HTTP 规则。推荐在包根目录添加 `modpackupdate.release.json`，包含与接口相同的 `pack-id`、递增 `release-id` 和 `version`，格式见 [发布协议](publishing-protocol.md)。客户端同时验证游戏、加载器和发布身份；编号小于或等于本地记录时不会自动更新。

每次触发兜底都会下载当前包到 `ModpackUpdate/downloads/`。没有内嵌发布元数据的普通包仍可使用：`versionId` 与本地不同时视为候选，但无法判断先后，也无法从包中独立验证 `pack-id`。此时即使开启静默更新，也必须人工确认可能降级的提示。内嵌元数据存在但无效时拒绝包，不退回无编号模式。作者必须保证 URL 始终提供当前版本；不使用旧缓存代替下载失败的当前包。两处来源都不可用时继续启动游戏。

完整包需要在游戏退出前下载、解析并验证，以便决定是否提示更新；下载前显示“跳过检查”窗口，并受总检查时限限制。跳过或超时会停止检查后继续游戏，尚未修改游戏文件。包内 `summary` 用作说明；`overrides/` 与 `client-overrides/` 合并生成客户端文件表，后者优先，忽略 `server-overrides/`。包内已有的覆盖文件直接提取，索引中只有下载链接的模组仍从原下载地址获取。

带编号的兜底更新会同步推进本地 `release-id`，与接口共用一个递增序列。无编号包保留旧编号并记录 `full-pack-sequence-known: false`；之后切回接口遇到不同版本时同样强制人工确认，直至成功安装有编号版本。接口恢复后相同版本跳过重复安装。旧预览版产生的兜底记录缺少此字段时，也按编号未知处理。

## 静默更新与冲突选择

| 情况 | `silent-update: false` | `silent-update: true` |
| --- | --- | --- |
| 没有新版或检查时离线 | 继续启动游戏 | 继续启动游戏 |
| 发现新版 | 显示版本与公告，由玩家选择更新或跳过 | 自动接受更新 |
| 当前或目标版本来自无编号兜底 | 必须确认版本先后无法验证 | 仍必须人工确认 |
| 接受更新且没有冲突 | 游戏退出后显示安装确认窗口 | 游戏退出后直接安装 |
| 本地文件冲突、待选择的可选文件 | 显示勾选列表 | 显示勾选列表 |
| 更新完成 | 显示结果，玩家从启动器重新启动 | 显示结果，玩家从启动器重新启动 |

静默模式仍会显示下载、安装进度和结果。有冲突仍显示选择框，冲突项默认勾选云端操作，玩家可以逐项选择、全选或全不选；新增可选文件仍默认不勾选。受保护路径不进入覆盖选择。

采用云端模组时，客户端读取模组 ID，将其他文件名下的同 ID 本地 JAR 一并改名禁用，包括缺少旧基线或此前手动改名的模组。这个联动优先于单独保留旧 JAR 的选择；若要保留旧版，应取消新版模组。未被云端替代的额外本地模组保留。禁用以整个 JAR 为单位，多模组 JAR 命中任一重复 ID 时整体禁用。受保护 JAR 不会被自动禁用，云端自身重复 ID 或仍冲突的目标文件会在写盘前报错，避免安装出两个同时启用的同 ID 模组。

同路径覆盖仍按备份/删除选项处理；不同路径替换保留旧文件为 `.jar.disable`，不删除，也不另复制一份备份。全不选会跳过表中的冲突项，其他自动处理项继续安装；若自动采用的新版模组与保留的旧 JAR 同 ID，仍按上述联动规则处理。

若跳过了新版模组，程序不会独立禁用无法确认已有替代品的旧模组。选中的新版下载后按模组 ID 核对：只有所有旧 ID 都由已采用的替代文件提供时，关联的禁用才保留。因为未选择的文件不会额外下载，这种情况下也可能保留其他无法确认关系的旧模组，结果会显示保留差异。全都采用、无冲突的普通移除仍正常禁用旧模组。

后续发布会重新检查已保留差异的模组，即使目标哈希未变，也会同时提供新版安装和旧版禁用选择；未采用新版时继续保留旧版。此前主动保留的旧模组也不会在下一版恢复成自动禁用。同一发布的普通启动仍跳过重复提示，普通配置文件继续按目标内容变更检查。

保护路径在生成安装计划时就已跳过，因此不会出现在冲突列表中。取消初次版本提示会继续当前游戏。取消独立程序中的安装确认时，游戏已经退出，需要从启动器重新启动。

安装完成后，即使玩家保留了部分差异，本地版本号仍会更新到已处理的目标版本，保留状态同时写入文件记录。后续发布再次改动相关路径时，会按保存的基线重新判断冲突。

## 备份和直接删除选项

默认 `delete-replaced-mods: false` 时，被同路径新版 JAR 覆盖的旧模组会移到下方目录。版本号取本次更新前的已安装版本，更新编号由程序生成。

```text
<游戏根目录>/ModpackUpdate/<旧版本号>/<更新编号>/mods/<原文件名>.jar
```

被覆盖的其他文件也按原相对路径备份，例如 `config/example.json` 会放到该版本备份目录下的 `config/example.json`。

启用 `delete-replaced-mods` 后，程序在安装期间保留用于失败恢复的旧文件，待全部文件安装成功且新版本记录提交后，清理本次被覆盖的旧 JAR 备份。配置文件等其他文件的备份仍保留。

安装确认窗口中的“直接删除被替换的旧模组，不保留备份”复选框，以 `delete-replaced-mods` 的配置值作为初始状态。在窗口修改只影响本次安装，持久修改需要编辑 `config.json`。

旧模组在新版清单中消失时，客户端将它改名为 `.jar.disable`。这个行为也适用于升级后 JAR 文件名改变时的旧文件，`delete-replaced-mods` 选项对这些禁用文件无影响。已有同名 `.disable` 时，程序使用带更新编号的禁用文件名。

## 保护路径

`protected-paths` 的每个条目都相对于游戏实例根目录，使用 `/` 分隔路径。

| 写法 | 匹配规则 |
| --- | --- |
| `options.txt` | 精确匹配根目录中的该文件 |
| `config/example-client.json` | 精确匹配指定的模组配置文件 |
| `config/example/` | 匹配该目录下的所有文件及子目录内容 |
| `saves/` | 匹配存档目录中的所有文件 |

匹配忽略大小写。目录条目以 `/` 结尾，文件条目使用完整相对路径。当前采用字符串精确匹配或目录前缀匹配，填写具体文件或目录即可，`*`、`**` 和正则表达式没有通配含义。

默认列表保护原版键位与视频设置所在的 `options.txt`、`optionsof.txt`、服务器列表 `servers.dat`、存档和截图。模组单独保存的键位或画面设置需要按其实际文件位置补充。

自定义数组会整体替换默认列表。添加自己的规则时，可保留默认条目后继续追加，例如下面的字段示例。

```json
{
  "protected-paths": [
    "options.txt",
    "optionsof.txt",
    "servers.dat",
    "saves/",
    "screenshots/",
    "config/example-client.json",
    "config/example/"
  ]
}
```

上面的示例只展示保护字段，合并到已有配置时保留更新地址、包标识等字段。`protected-paths: []` 会清空用户设置的保护列表。即使清空列表，`ModpackUpdate/` 仍由客户端保留，更新安装会跳过发布内容中的该目录。

保护规则同时跳过覆盖、新增和旧模组禁用。即使某个保护文件尚不存在，更新也会跳过对该路径的首次创建。

## 网络超时

`timeout-seconds` 的有效范围为 2–120 秒。低于 2 的值按 2 秒处理，高于 120 的值按 120 秒处理。

连接和单次 HTTP 请求使用该值。发布元数据及不超过 16 MiB 的文件响应体也使用该秒数限制读取时间。声明大小超过 16 MiB 的文件响应体最多允许读取 30 分钟。每次重定向或备用下载地址尝试会重新发起请求，因此这个选项表示单次网络阶段的限制。

正常启动检查只获取发布元数据。接受更新并退出游戏后，独立程序才下载整合包索引及需要安装的内容。启用完整包兜底且接口清单下载失败时，启动检查还会下载并解析完整包。已经完整下载且校验通过的安装文件缓存会复用。

`check-timeout-seconds` 是检查阶段的总预算，包含接口失败后的完整包下载和解析；不限制玩家停留在确认窗口的时间。检查超时先由更新器取消网络与解析，引导层再给 5 秒退出宽限；若更新器未正常结束，会终止它，确认退出且无未完成事务后才继续游戏。更新器尚未报告阶段时另有 120 秒启动保护。用户接受更新后的安装下载采用上面的单次下载限制。

## 缓存、空间与备份保留

启动检查前和更新器结束时，在持有实例锁且没有未完成事务的情况下清理缓存。只处理程序认识的下载文件，按时间优先清理旧缓存；正在安装时允许暂时超过 `cache-max-mib`。安装前检查所需副本空间，并预留 64 MiB；下载和提取也检查可用空间。空间估算无法预防其他程序随后占用磁盘，安装失败仍走恢复流程。

超过 14 天的旧日志及非当前更新器副本会清理。备份默认全部保留；例如 `backup-retention-count: 3` 会保留最近三次带完成标记的备份事务。自动清理只识别本版本写入 `.modpackupdate-backup.json` 标记的目录，旧版和未知目录保留供人工管理，存在未完成事务时不执行清理。

## 独立修复与重新处理差异

先关闭此游戏实例，再使用构建产物中的独立 updater JAR：

```powershell
java -jar ModpackUpdate-updater-0.3.0-preview.6.jar repair "D:/Packs/MyPack" "1.20.1" "0.16.10" "fabric-loader"
java -jar ModpackUpdate-updater-0.3.0-preview.6.jar repair "D:/Packs/MyNeoPack" "1.21.1" "21.1.266" "neoforge"
```

`repair` 不依赖游戏成功启动，也不受 `enable: false` 限制。存在事务时先恢复；否则允许重新处理更新源提供的相同版本，检查目标文件，即使之前选择了保留差异。冲突仍需勾选，不会强制覆盖保护文件。该命令也可以安装源中的更新版本，但拒绝已知编号更小的版本。需要有图形界面的 Java 环境；无编号版本仍要求确认。若源不再提供当前版本，只能使用可用的更新版本或由作者恢复对应来源。

安装结果为 `complete` 表示本次处理没有保留已知差异，`modified` 表示保留了文件或旧模组；不代表经过了全部模组依赖兼容性验证。普通启动不反复提示同一份保留选择，可通过 `repair` 再次处理。

事务会先记录已开始的操作数量，再执行文件变更；安装临时文件在替换前刷盘，目录刷盘在平台支持时执行。自动化测试覆盖各阶段中断和重复恢复。这些措施不等于对任意硬件断电的绝对保证；不支持目录刷盘的文件系统、磁盘硬件与真实启动器仍需单独验证。

恢复禁用操作时，必须找到校验通过的禁用文件，或者确认原文件已完整恢复。两者都缺失、或原文件已被外部修改时保留事务并报错，不会把实例标记为恢复成功。

## installed.json

该文件只保存版本、状态和文件基线索引引用。启动检查不读取文件基线；发现候选更新、准备安装时才从 `file-indexes/{files-index}.json` 校验并加载基线。作者为初始发行版本生成这些文件，成功安装后由客户端自动维护。旧 v1 内联基线继续兼容，成功安装后自动迁移。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `schema-version` | 整数 | 安装记录格式，当前为 `2`，仍可读取旧 `1` |
| `pack-id` | 字符串 | 整合包标识 |
| `release-id` | 整数 | 最近成功处理的发布编号 |
| `version` | 字符串 | 最近成功处理的展示版本 |
| `full-pack-fallback` | 布尔值 | 最近安装是否来自完整包兜底，旧记录缺省为 `false` |
| `full-pack-sequence-known` | 布尔值 | 该兜底安装是否携带统一发布编号；缺省为 `false` |
| `installation-status` | 字符串 | `complete` 或 `modified`；旧记录可结合 `files.*.retained` 判断 |
| `transaction-id` | 字符串 | 最近成功提交的安装事务编号，初始记录可为空字符串 |
| `files-index` | 字符串 | 基线索引原始字节的 SHA-512，同时用作 `file-indexes/` 下的文件名（加 `.json`） |

基线索引格式为 `{ "files": { ... } }`，`files` 以游戏根目录相对路径为键，每个条目包含以下字段。旧 v1 将相同对象直接放在 `installed.json` 内。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `sha512` | 字符串或 `null` | 最后采用的作者原始内容哈希，缺少可信旧基线时可为空 |
| `target-sha512` | 字符串 | 最近处理的目标内容哈希 |
| `retained` | 布尔值 | 对目标文件是否保留了本地差异或跳过了安装 |
| `optional` | 布尔值 | 最近处理版本中该文件的客户端可选属性 |

哈希字符串使用 128 位小写十六进制。作者原始哈希由已发行版本的文件内容计算，可以通过独立程序的 `seed` 命令生成。玩家修改后的磁盘文件无法提供可靠的旧原版基线。 [基线格式](publishing-protocol.md) · [初始打包流程](packaging.md)

`installed.json` 缺失时，程序以 `release-id: -1`、`version: "uninitialized"` 和空文件表处理当前实例。现有文件与新版内容一致时直接采用，内容不同时进入缺少基线的冲突选择。清单外模组通常保留；与已选云端模组同 ID 时按联动规则禁用。

保留 `installed.json` 及其引用的索引，才能持续识别原受管文件、旧版本与玩家差异。提交先写索引，再原子替换头文件；缺失或哈希不符的索引会阻止安装。未引用的旧索引目前保留，不受下载缓存清理影响。版本字段和事务编号参与更新判断与中断恢复，应交由生成工具及客户端维护。

## 常见问题

| 现象 | 检查位置或处理方式 |
| --- | --- |
| 启动后没有检查新版 | 核对 `enable`、URL、`pack-id`，并查看远程 `release-id` 是否高于本地值 |
| 配置错误后游戏仍正常启动 | 查看 `ModpackUpdate/runtime/check-*.log`，确认 JSON 格式和字段类型 |
| 开启静默仍出现选择框 | 查看列表中是否有本地冲突、可选文件或可选改为必需的文件 |
| 全选后某个设置仍被保留 | 检查 `protected-paths` 中是否包含该文件或上级目录 |
| 开启删除选项后仍有 `.disable` 文件 | `.disable` 用于禁用清单中消失的旧模组，覆盖备份按单独规则清理 |
| 关闭更新后仍进入恢复窗口 | 查看是否存在上次安装留下的事务记录，完成恢复后再重新启动 |
| 发现新版，游戏退出后提示版本不匹配 | 核对索引声明的 Minecraft、加载器类型和版本是否与实例完全一致，各平台依赖字段见 [发布协议](publishing-protocol.md) |

首次发行时将 `config.json`、生成的 `installed.json` 和其引用的 `file-indexes/*.json` 放进 `.mrpack` 的 `overrides/ModpackUpdate/config/`。已有实例的这些文件由本地管理，后续发布中的同名配置会被保留目录规则跳过。 [打包流程](packaging.md)
